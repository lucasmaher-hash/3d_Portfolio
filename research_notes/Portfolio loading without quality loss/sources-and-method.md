# Research sources and method

28 October 2026. Scope expanded by Lucas during research: small quality loss acceptable on desktop and mobile; compare increments, find visible degradation, also improve loading without quality loss. Subsequent real iPhone screenshots exposed blocky floor artifacts from the previously deployed full-resolution mobile UASTC pack; the floor is now explicitly exempt from every compression tier and restored as its original PNG in hotfix 56e5b2f. This user evidence overrides small headless-image error scores.

## Source-backed mechanisms

- Three KTX2Loader detects GPU formats and transcodes Basis containers; dimensions, mip chain, linear colour space and RGBM alpha must be preserved or deliberately regenerated. https://threejs.org/docs/pages/KTX2Loader.html
- Basis UASTC RDO trades image error against entropy/file size. Lower RDO values preserve more quality. ETC1S is a separate smaller/lower-quality codec. The encoder used is pinned Basis Universal 1.16.3 from @gpu-tex-enc/basis@1.16.4; exact flags were checked against its own help, rather than assuming latest v2 options apply. https://github.com/BinomialLLC/basis_universal and https://github.com/BinomialLLC/basis_universal/wiki/UASTC-implementation-details/3e2e46fef801577f8f741a1c2947a372f5a29d47
- Preload/earlier discovery can reduce late request chains, but excessive preloads contend for bandwidth. The implementation overlaps actual scene dependencies, not all portfolio content or speculative 2D-page downloads. https://web.dev/articles/preload-critical-assets
- PMREMGenerator explicitly supports precompiling its conversion shader during texture download. https://threejs.org/docs/pages/PMREMGenerator.html
- Three meshopt reduces download size; it does not directly improve frame rate. Current gallery already uses EXT_meshopt_compression plus quantization, so blindly applying the convenience meshopt/quantize transform again would be another quality change. No geometry simplification was made. https://gltf-transform.dev/modules/extensions/classes/EXTMeshoptCompression and https://gltf-transform.dev/modules/functions/functions/meshopt
- EXRLoader parses compressed HDR sources; HDR conversion/PMREM is setup work in addition to downloading. These reflection probes remain unchanged. https://threejs.org/docs/pages/EXRLoader.html
- MeshBVH supports serialize/deserialize and workers; these can move collision setup out of the critical path, but serialized buffers add transfer cost and workers can transfer geometry buffers while unavailable to other setup code. Current change overlaps the existing exact BVH build with independent downloads, without changing the tree or collision geometry. https://github.com/gkjohnson/three-mesh-bvh/blob/master/API.md and https://github.com/gkjohnson/three-mesh-bvh/blob/master/README.md
- encodedBodySize is the body before gzip/Brotli decoding; it is not the decoded asset byte count, and cached resources still report a body size. Cold tests explicitly disabled HTTP cache. Parent-document Resource Timing does not include nested iframe subresources or cross-origin entries without Timing-Allow-Origin. https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming/encodedBodySize and https://www.w3.org/TR/resource-timing/
- CPU throttling is relative to host hardware; desktop emulation does not reproduce iPhone CPU/GPU architecture. https://developer.chrome.com/docs/devtools/device-mode and https://developer.chrome.com/docs/devtools/performance/reference

## Actual delivery audit

Live GitHub Pages already served the raw 7,301,384-byte colour LUT as about 2,172,896 gzip bytes and the 18,622,956-byte GLB as about 5,746,199 gzip bytes. Cache-Control max-age=600 and Vary Accept-Encoding were present. Do not claim adding gzip would newly save the difference. Content encoding reduces transfer while preserving decoded representation: https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Encoding . Stronger transport codecs or a CDN migration are not assumed necessary from this evidence.

The observed serial chain was model -> scene metadata -> colour LUT -> seven HDR probes -> lightmaps -> rounded lamp -> seven original podium PNGs one by one -> wall-seams JSON -> warmup. On mobile the podium PNGs duplicated texture content already downloaded in compressed form. The seven cap fields total 458,752 Float32 bytes. Together with two wall-seam attributes, the exact cached data is 3,021,528 bytes raw, about 1,414,900 gzip bytes. Its SHA-256 before and after the refactor is 57c0dcb65f83c466eecf0832d39d7702d6fd0d53dc57f2a6b8bed50bc36fa3a9.

## Experiments

Full-resolution original PNGs: 21.69 MiB; previous full-resolution UASTC no-RDO: 18.29 MiB. UASTC level 3 with linear metrics, forced alpha, box/clamped mipmaps, RDO 0.5 / 2 / 6: 15,957,368 / 14,501,957 / 13,634,954 bytes. Full-resolution ETC1S q255: 4,294,027 bytes, visibly blotchy floor; rejected. All-half UASTC RDO2: 4,257,206 bytes, floor artifacts; rejected. Selected: 23 half-dimension UASTC RDO2 maps (3,791,980 bytes) plus original PNG floor, about 5.4 MiB combined. Geometry, materials, HDR reflection probes and OCIO colour LUT remain unchanged.

Five fixed gallery views, 1440×1000 and 390×844 at DPR2, captured with fixed camera/project poses. Prototype full-resolution UASTC RDO variants averaged 0.18–0.26 RGB code values absolute error on a 0–255 scale; selected selective-size prototype around 0.3, stronger ETC1S around 1.1. These image metrics are descriptive, not a perceptual acceptance threshold. Real mobile floor artifacts were visible despite low global scores, hence the original floor exception. Comparison images in this folder show compression prototypes; their compressed floor is NOT the final shipped floor.

## Timing method

Chrome 156.0.8078.48, headless ANGLE Metal on Apple M4; fresh browser contexts, HTTP cache disabled. Readiness is actual scene-ready, not a decorative animation timeout. Exploratory live run: desktop 15.88s, mobile 20 Mbps/80ms/4× CPU 24.45s. These are not compared directly with localhost timings as a universal speedup.

Controlled before/after used fixed production-build snapshots served with HTTP gzip on localhost, same browser/hardware and 20 Mbps, 80ms, 4× CPU for the mobile case. Original: 22.94s readiness / 38.7 MiB parent-document encoded payload. Final: 12.96s / 21.4 MiB. Unlimited-network desktop: 2.30s -> 1.56s. One paired run is evidence of direction and magnitude, not a promised phone result; driver caches, origin connection and thermal state vary. A prototype measured 12.43s/21.7 MiB before restoring the original PNG floor; final result supersedes that prototype. No benchmark overlapped another browser workload in the final pair. Measurements are in controlled-before.json and controlled-final.json.

Local setup-only timing before changes showed about 725ms collision build, 249ms cap fields, 376ms seam calculations, 260ms warmup on this host. The exact cached fields remove the cap/seam calculations; BVH is overlapped, not removed. Existing warmup remains to avoid first-walk shader/texture stalls. Welcome animation (~3.65s reveal) was not shortened as a fake loading improvement; scene readiness is a separate gate.
